# Proxy Monetization Research — Curated Referral Section

**Feature slug:** `proxy-monetization`
**Date:** 2026-07-05
**Decision already made (input, not a finding):** START with an **affiliate/referral** model (hybrid — reselling is a possible later phase). The in-app section is a **curated list** (~5–10 recommended providers with referral links + basic compare), **NOT** a full live-priced catalog.
**Audience:** anti-detect browser for AI agents + human operators, tens–low-hundreds of active users, bootstrap budget, solo/tiny team, privacy-sensitive.

> **How to read the citations.** Every factual claim links to its source URL. "Unverified" = could not be confirmed on an official page. Where a provider's *marketing page* and its *binding legal terms* disagree, both are reported and the legal terms are treated as authoritative. Figures were gathered in July 2026; affiliate terms change frequently, so re-confirm at signup before relying on any exact number.

### Pattern for MultiZen

The niche is a ~50/50 split. **Resell camp** (Multilogin, GoLogin, Dolphin) bills metered proxy traffic inside the app as recurring, sticky revenue — higher margin but requires provider/wholesale relationships, billing, support, and abuse handling. **Affiliate camp** (AdsPower, Undetectable) deliberately sells *no* proxies, stays provider-agnostic, and monetizes via referral directories with coupon codes. AdsPower is the closest precedent to MultiZen's chosen approach: a curated recommended-providers page, provider-agnostic, referral-monetized, no resale. This validates the decision to **start affiliate-only** and keep resale as a later phase.

## 3. Data / freshness for the curated in-app section (no hacks)

The section is a curated ~5–10 provider list, not a live-priced catalog, so freshness needs are low: the data is essentially provider name, type, geo, an **entry-price *range*** ("from $X/GB"), a referral URL, and notes. This changes maybe monthly. The right design is a **hosted, versioned static JSON file the app fetches, with the JSON committed to git and cached locally with an offline fallback**.

### Recommended: static JSON, git-committed, served from infra MultiZen already runs

MultiZen already publishes desktop releases via **GitHub Releases** (`multizenteam/multizen-browser`, `releaseType: release`, stable asset URLs), per [`apps/desktop/electron-builder.yml`](../../apps/desktop/electron-builder.yml). It also has a landing site at **getmultizen.com** with hardcoded download links, and a **Hetzner** box is already planned for the analytics ping ([`specs/BACKLOG.md`](../BACKLOG.md)). So there is no new infra to stand up — three viable hosts already exist.

#### Hosting options compared

| Option | Freshness / update flow | Caching | Cost / ops | Privacy | Verdict |
|---|---|---|---|---|---|
| **A. GitHub raw** (`raw.githubusercontent.com/multizenteam/.../providers.json`) | Edit JSON → commit → push; live immediately on the default branch | Short GitHub cache (~5 min) — good for correctness, re-fetched often | Zero — reuses existing repo, git *is* the versioning/audit trail | GitHub sees the requester IP; no user data sent. Acceptable but it's a third-party host | **Recommended primary.** Zero ops, git-native version control, matches how releases already ship |
| **B. jsDelivr CDN over the same GitHub file** (`cdn.jsdelivr.net/gh/multizenteam/multizen-browser@<tag>/providers.json`) | Same git flow; pin to a tag for permanent caching, or use `@latest` | Strong global CDN cache; files persist even if deleted from GitHub | Zero | jsDelivr (Cloudflare/Fastly) sees IP; no user data | **Good fallback / mirror.** Better global perf; pin a tag to control cache. Source: [jsdelivr.com/github](https://www.jsdelivr.com/github) |
| **C. Static file on getmultizen.com** (e.g. `getmultizen.com/data/providers.json`) | Deploy step publishes the file with the site | Depends on the site's CDN/headers | Low — first-party domain, full control of headers/privacy policy | **Best privacy story** — first-party, one domain, no extra third party, publishable no-log policy | **Recommended if the site has a real deploy pipeline.** Cleanest trust story for a privacy audience |
| **D. Hetzner box static endpoint** (nginx serving a file) | git pull/checkout on server (matches deploy-via-git norm) | Set `Cache-Control` yourself | Low but you own uptime/patching | First-party, self-hosted, no-log-able | Fine, but overkill for one JSON file unless the analytics box already serves static assets |

**Recommendation:** ship the JSON as a **git-committed file in the repo**, and serve it from **getmultizen.com** as the primary URL (best privacy/trust story for this audience) with **GitHub raw or jsDelivr as an automatic fallback URL** if the first fetch fails. This keeps the update workflow trivial (edit JSON → PR → merge → deploy) with git as the full version history and review trail — no admin panel, no database. A tiny admin UI is unnecessary at this scale and adds a call-home surface; avoid it.

### Schema (proposed)

```jsonc
{
  "version": 3,                        // integer, bumped each update; app can compare/skip
  "updated": "2026-07-05",             // ISO date, shown as "prices last checked"
  "disclosure": "MultiZen may earn a commission if you buy through these links. It never costs you more, and it does not affect the order or what we recommend.",
  "providers": [
    {
      "id": "nodemaven",
      "name": "NodeMaven",
      "types": ["residential", "isp", "mobile"],   // residential | isp | datacenter | mobile
      "geo": "150+ countries",                       // human string, not a live figure
      "entryPrice": "from $3.5/GB",                  // RANGE / "from", never an exact live price
      "url": "https://nodemaven.com/?ref=multizen",  // referral URL (see §4 on params)
      "noRefUrl": "https://nodemaven.com",           // plain URL for a "visit without referral" toggle
      "bestFor": "Multi-accounting, sticky sessions", // short compare tag
      "notes": "Built by the Multilogin team; IP quality filtering.",
      "featured": true                                // optional: highlight 1-2
    }
    // ... 5-10 total
  ]
}
```

Keep `entryPrice` a **"from $X" range**, not an exact live number, and keep it as a display string (not a computed field) so a human sets it deliberately. This is the core anti-staleness lever: you are advertising an order of magnitude and a link-out, never quoting a live checkout price you'd be wrong about.

### Caching + offline fallback

1. On the relevant screen (not on startup — see §4), fetch `providers.json` with a short timeout (e.g. 5 s).
2. On success, write it to the app's local data dir (e.g. `providers.cache.json`) with a timestamp.
3. On failure/offline, render the last cached copy; if none, render a **small JSON bundled in the app build** as the ultimate fallback so the section is never empty.
4. Optionally skip the network entirely if the cache is < N hours old (a range like 24 h is plenty — this data barely changes).
5. Never block UI on the fetch; the section renders instantly from cache and silently updates.

### Avoiding stale/incorrect pricing

- Show **ranges** ("from $X/GB"), never exact live prices.
- Show the `updated` date as "prices last checked YYYY-MM-DD" so users know it's indicative.
- **Link out** to the provider for real, current pricing rather than reproducing their price table.
- A short disclaimer: "Prices are indicative and set by the provider; check their site for current rates."

## 4. Privacy / trust considerations

The audience actively distrusts tracking, so the catalog fetch and the referral links both need to be defensible.

### The catalog fetch must be non-tracking

- **Plain static GET, no query params, no headers carrying identity.** No user ID, no install ID, no telemetry piggybacked on this request. A privacy-audit reader should see nothing but `GET /data/providers.json`.
- **Serve from a first-party domain (getmultizen.com)** as primary so there's one clear controller with a publishable no-log policy; this is a materially better story than a GitHub/CDN IP-logging third party, though the fallback to those is acceptable since the request still carries no user data.
- **Make it lazy and arguably optional.** Fetch only when the user opens the "Proxies / Recommended providers" screen, not on launch — so an install that never opens that screen never makes the call. Consider a settings toggle to disable the remote refresh entirely (falls back to the bundled snapshot), consistent with the project's "no silent call-home" ethos noted for the analytics feature ([`specs/BACKLOG.md`](../BACKLOG.md)).
- **Because it's open source,** the fetch code and the exact URL are auditable — lean into that: document it in the README/privacy note.

### Referral links: disclosure and acceptability

- **Disclosure is both an FTC expectation and a trust necessity here.** FTC guidance: disclose any material connection (commissions) in clear, plain language, placed where the user sees it *before* clicking — e.g. "This post/section contains affiliate links; we may earn a commission." Sources: [impact.com/.../affiliate-link-disclosure](https://impact.com/influencer/affiliate-link-disclosure/), [termly.io/.../ftc-affiliate-disclosure](https://termly.io/resources/articles/ftc-affiliate-disclosure/), [referralcandy.com/.../ftc-affiliate-disclosure](https://www.referralcandy.com/blog/ftc-affiliate-disclosure). Ship the disclosure string inside the section (it's in the schema above), visible above the provider list.
- **Embedding affiliate params is acceptable to this audience *if* it's transparent and non-coercive.** The competitors this audience already uses all do it: AdsPower's "recommended providers" directory is openly a partner/coupon page; GoLogin and Dolphin run affiliate review directories with discount codes. Sources: [help.adspower.com/.../recommended_proxy_providers](https://help.adspower.com/docs/recommended_proxy_providers), [gologin.com/best-proxy-server-services/proxy-store](https://gologin.com/best-proxy-server-services/proxy-store/). The norm in the space is coupon-code framing ("save 20% with code X"), which reframes the affiliate link as a *benefit to the user* rather than a tax — this is the friendliest framing for a skeptical audience.
- **Best-practice touches that build trust with anti-detect users specifically:**
  - Offer a **"visit without referral" plain link** alongside the referral link (the schema's `noRefUrl`). Costs almost nothing and signals good faith; very few will use it, but its presence disarms the "you're just monetizing me" objection.
  - Prefer **discount/coupon framing** where the provider offers a code, so the user gets something.
  - State plainly that **referral status does not change the ranking or which providers are listed** (and honor that — order by genuine fit, not commission).
  - Keep it **honest and comparative** — note weaknesses, not just strengths. This audience punishes shill lists. (Caveat: NetNut's affiliate contract §7.2 restricts "negative" content — a reason to weight it lower or omit it, since honest comparison is the whole trust play.)

## 5. Realistic economics at this scale

Be blunt: at tens–low-hundreds of active users, affiliate proxy revenue is a **rounding error in absolute terms**, but the **build cost is also very low**, so it can still clear its own bar — mainly as a foundation for later scale and as validation, not as income today.

### The mechanics

- Proxy affiliate is B2B with high AOV and mostly recurring, so **per-converting-customer value is unusually high**: industry commentary cites $500–$2,500 lifetime per referral for residential programs, driven by business AOV and recurring revshare. Source: [affmaven.com/proxy-affiliate-programs](https://affmaven.com/proxy-affiliate-programs/), [afftank.com/blog/proxy-affiliate-programs](https://afftank.com/blog/proxy-affiliate-programs). Realistically for a solo indie audience buying small residential plans ($10–$50/mo, not $1k enterprise), expect commission of a few dollars to low-tens of dollars *per month* per active referred customer on a 10–50% recurring share, occasionally a larger one-off.
- **The binding constraint is conversion volume, not commission rate.** With ~100–200 active users, only a fraction ever open the proxies screen, a fraction of those click out, and a fraction of those buy and stay. A generous funnel: 150 active → say 40% open the section (60) → 15% click a referral (9) → 20% convert and retain (≈2 paying referrals). Those are illustrative assumptions, not measured data — flag as an estimate.

### Rough expectation (illustrative, not a promise)

- **Order of magnitude at ~150 users:** a handful of converted referrals in the first months; if each yields ~$3–15/mo recurring, that's roughly **$10–60/mo**, i.e. low-hundreds of dollars/year. A single referral who buys a bigger residential plan can double that; a dry month can be $0. **Minimum payout thresholds bite hard here** — NodeMaven ($100 crypto) or Infatica ($100) could take many months to reach, whereas **Webshare ($10) and SOAX ($10)** actually pay out at this scale. This is a concrete reason to weight low-threshold programs first.
- **Is it worth the build?** Yes, narrowly, *because the build is cheap*: one static JSON file + one screen + a fetch-with-cache. There's no ongoing ops (no resale, no billing, no support). It also does double duty as a genuinely useful feature (users need proxies and will ask "which one"), and it lays the rails for the later resale phase where margins are real. If the build were expensive (a live-priced catalog, a marketplace, billing), the honest answer at this scale would be **no** — which is exactly why the "curated static list" scope is the right call.
- **What would move the needle** isn't the in-app section at 150 users; it's content/SEO and audience growth (the 65-user Discord, the ~230 visits/mo). The in-app section captures intent from people already choosing a proxy; it won't manufacture demand. Set expectations accordingly: treat first-year affiliate income as *validation signal + beer money*, and the strategic value as *owning the proxy touchpoint before adding resale*.

1. **Model:** affiliate-only to start (as decided). This matches the AdsPower / Undetectable precedent and needs no billing, wholesale, or support. Resale is a later phase.
2. **Starting provider set (~6, ordered by fit + terms + payout-reachability at low scale):**

5. **Fetch behavior:** lazy (only on the proxies screen), short timeout, cache locally, bundled-JSON ultimate fallback, optional settings toggle to disable remote refresh. No user data on the request — plain GET.
6. **Disclosure/trust:** visible affiliate disclosure above the list; coupon-code framing where available; a "visit without referral" plain link per provider; explicit statement that referral status doesn't affect ranking; honest comparative notes.
